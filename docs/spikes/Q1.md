# Q1: Which refund endpoint accepts subscription transaction IDs?
Owner: Om · Date: 2026-10-29

## Answer (one paragraph)
**Use `POST /v2/payments/captures/{id}/refund`.** The `id` values from `GET /v1/billing/subscriptions/{id}/transactions` are directly usable as v2 capture IDs: `GET /v2/payments/captures/{id}` returns the subscription payment, and a partial refund succeeds (201). The legacy `POST /v1/payments/sale/{id}/refund` also works on the same ID, but it belongs to the deprecated v1 Payments API, so we don't build on it. The v2 endpoint honours `PayPal-Request-Id`. Replaying the same refund with the same key returned **200 with the same refund id and no second refund**, so the action engine can retry refunds safely without first checking the refund list. Refunds don't change the subscription: it stays `ACTIVE`, and the capture moves to `PARTIALLY_REFUNDED`.

## Impact on the design (link the ADR if one was needed)
- ARCHITECTURE §6.1 "Refund" row: the endpoint is `POST /v2/payments/captures/{transactionId}/refund` with `PayPal-Request-Id`. The "otherwise check the refund list" fallback isn't needed. No ADR, because this resolves an open choice rather than changing the design.
- Partial refunds work, so `refund_partial` offers can refund any amount up to what's left on the payment.
- **Side finding for the gateway (M1):** the subscription's `billing_info.last_payment.amount.value` came back as `"1.0"`, not `"1.00"`. The transactions list and the capture use `"1.00"`. The gateway must normalise PayPal amounts to two decimals before they reach our `Money` schema, which requires `\d+\.\d{2}`.
- Setup gotcha for teammates: sandbox accounts created with country **India** fail at subscription approval with a generic "Things don't appear to be working" page, because PayPal doesn't support domestic payments in India. Create **US** business and personal sandbox accounts.
